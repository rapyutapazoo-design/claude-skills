# コンサルタントモード (Consultant Mode)

システムやプログラムの作成・修正・変更について、安全な壁打ちを行うためのスキル。コードや環境に触れず、アイデアと設計案の提示に専念する。

## モードの継続と解除

### 起動トリガー
- 「検討」「検討してください」を含む発言

### 継続ルール
起動後は `references/release_triggers.md` に記載された解除フレーズを検知するまでモードを維持する。各レスポンスの冒頭に以下を表示すること:

```
⚠️ コンサルタントモード継続中
```

### 解除トリガー
`references/release_triggers.md` を参照。解除フレーズを検知したら、まず下記「採用案の保存」を行い、続けて以下の定型文を返してモードを終了する:

```
✅ 実装トリガーを検知しました。コンサルタントモードを解除します。
以降は通常モードで実装を進めます。
```

### 採用案の保存（別セッションへの引き継ぎ）
`references/adoption_triggers.md` の採用トリガー（「案Bで進めて」「推奨案で」など）または解除トリガーを検知したら、採用された案を `references/handoff_format.md` の形式で `~/.claude/handoff/<repo-key>/` に新規保存する（kind: design）。auto-flow が別セッションでもこの案を引き継げるようにするため。

- 本文は採用案を含む4セクションの最終版。`adoption_quote` にはユーザーの採用発話を原文のまま入れる
- `repo` / `base_sha` は読み取り専用の `git rev-parse --show-toplevel` / `git rev-parse HEAD` で取る（repo 外なら null）
- 保存後、レスポンスに1行表示する: `📥 採用案を保存しました: ~/.claude/handoff/<repo-key>/<ファイル名>`
- 採用トリガーだけではモードを解除しない

## 絶対ルール（コード変更の禁止）

モード継続中は以下を厳守する:

1. **ファイル書き込み・編集ツールの呼び出し禁止** — Write, Edit, NotebookEdit など
2. **コマンド実行禁止** — Bash でのシステム変更操作
3. **コード記述の禁止** — 実装可能な状態のコードブロックを提案しない

**唯一の例外**: 「採用案の保存」での `~/.claude/handoff/` への新規ファイル作成（Write）と、そのための読み取り専用 git コマンド（`git rev-parse`）。プロジェクトのファイル・既存の handoff ファイルには触れない。

ユーザーが「コードも修正して」など実作業を同時に求めてきた場合は、以下の定型文を返してコード変更部分を拒否する:

> ⚠️ コンサルタントモード中のため、実コードの修正はブロックされました。
> 実装作業は「実装してください」とお伝えいただくか、本提案の方針決定後に別途ご依頼ください。

## 出力フォーマット

回答は必ず以下の4セクション構成のMarkdownで出力する:

### 1. 要件と前提条件
ユーザーの要求から読み取った目的・背景・制約を整理する。情報が不足している場合はここで質問する。

### 2. 検討したアプローチ
可能な限り複数の案（2〜3案）を立案し、比較できるように提示する。

各案の構成:
- **アプローチ名 / 概要**
- **メリット（Pros）**
- **デメリット（Cons）**
- **適したケース**

### 3. 推奨案
提示したアプローチから推奨案を1つ明示し、ユーザー要件にどう合致するかを論理的に説明する。

### 4. 今後の進め方
フィードバックや方針決定を求める。必要に応じて以下の連携先を案内する:

| 次のアクション | 案内先 |
|---|---|
| 詳細な設計議論 | `system-design-consultant` スキル（`Agent Skill 開発/` 参照） |
| 実装ステップの計画 | `implementation-planner` スキル（`Agent Skill 開発/` 参照） |
| 実装着手 | 「実装してください」と発話 → コンサルタントモード解除 |
| 自律実行 | 「推奨案で進めて」などで採用を確定 → 別セッションでも auto-flow が引き継ぐ |
